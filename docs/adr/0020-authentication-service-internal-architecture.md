# Authentication Service internal architecture

**Authentication Service** is a thin ports-and-adapters process, same as Owner & Pet Manager (ADR-0018): Fastify HTTP adapters validate and map; use cases orchestrate; Drizzle/PostgreSQL, the Owner & Pet Manager client, the mail channel, and the signer sit behind ports. Use cases return typed results and take a clock. The HTTP adapter maps them to Problem Details and collapses cases the requirements say a caller must not tell apart. Problem Details URNs for this service are ADR-0022. The platform-service authenticator establishes the actor on the revoke route only; the use case allows only `owner-pet-manager`. Route-handler rules and Nest-style modules stay rejected (ADR-0007, ADR-0018). Ensure platform client is the exception to adapter validation: the adapter only requires a JSON object, and the use case returns unauthorized before it validates the client secret, the active flag, and the service id (AUTH-FR-008).

Three aggregates: **Owner session**, **Password reset**, and **Platform client**. Rate-limit events are a port, not an aggregate. Ids are UUID v7. Owner access tokens and platform-service access tokens are EdDSA JWTs from one Ed25519 key (`alg` pinned, no `kid`, no `jti`) and are not stored. Refresh tokens and reset tokens are 32-byte opaque secrets, sent as unpadded base64url; only SHA-256 verifiers are stored. Platform client secrets stay Argon2id (ADR-0012). An Owner session stores a SHA-256 fingerprint of the Owner’s Argon2id string, not the string.

An Owner session keeps every refresh verifier until the session ends, so any already-rotated refresh token revokes that session (AUTH-FR-002) and a miss revokes nothing. Rotation runs in one locked transaction and only after Owner & Pet Manager has confirmed the Owner is active and the fingerprint matches. A concurrent second presentation of the token that just rotated revokes the session. If that call cannot be completed, the token stays current. If Owner & Pet Manager reports deactivation or a fingerprint mismatch, every Owner session for that Owner is deleted. Logout of the current refresh token deletes that session only; logout of any other token succeeds and leaves a successor in place. Access tokens are always 15 minutes, even when the session ends sooner. The process refuses to start without `JWT_PRIVATE_KEY_PATH` (the Ed25519 private key) or `RESET_LINK_TEMPLATE`. The template contains one `{token}` placeholder, and the message body is the template with that placeholder replaced by the Reset token. The v1 mail adapter writes that message to a file path the operator sets and does not write the Reset token to service logs. The reset message is sent before the verifier is stored. Completion calls Owner & Pet Manager first; one local transaction then marks the Password reset used and deletes every Owner session for that Owner. The revoking transaction deletes the session and its verifiers. An in-process sweep runs every 60 seconds and deletes sessions past their absolute expiry and Password resets past 20 minutes.

Rate limits are sliding windows in this service’s Postgres. A validation failure reserves nothing. Any other login, client-credentials, or reset attempt reserves a slot in a short transaction and releases the lock before Argon2id or an outbound call; that reserved slot counts until the attempt finishes. A rejected login or client-credentials attempt keeps its slot. A successful login or client-credentials grant deletes the slot it reserved, as does a login or client-credentials attempt that cannot be completed. A reset attempt keeps its slot when a link is sent and when the email matches no active Owner. It deletes that slot when Owner & Pet Manager cannot be reached or the mail send fails. Login and client-credentials always run one Argon2id verify (a startup dummy hash when there is no real one). The no-send reset path waits out a configurable floor, default 1 second, kept under 2 seconds. Owner & Pet Manager and mail abort at 5 seconds. The caller address is the one this service sees. Service logs stay as in ADR-0013.

**Considered options.** JWT refresh tokens—rejected; reuse detection needs server state, and a JWT would look like an access token. Keeping only the current and previous verifier—rejected; AUTH-FR-002 requires any already-rotated token to revoke the session. A short grace when two refreshes race—rejected; the loser revokes the session. Copying the Argon2id password hash onto the session—rejected in favor of a fingerprint. Persisting a Password reset before the mail channel accepts—rejected; a failed send must not leave a usable grant. Argon2id verifiers for refresh and reset secrets—rejected; those secrets are 256-bit and login already pays for a password Argon2id. Process memory or Redis for rate limits—rejected; this stack has Postgres per service and no Redis, and memory would split the caps. Rotating a refresh token before Owner & Pet Manager answers—rejected; a failed call would turn the retry into reuse and kill the session. Clamping the access token to the session’s remaining time—rejected; AUTH-FR-002 fixes the access token at 15 minutes. A second signing key for platform tokens, or RS256/ES256—rejected for v1; one Ed25519 key matches the maintainer guide.

**Consequences.** Diagrams: `docs/architecture/authentication-service.mmd`, `docs/architecture/system-class-diagram.mmd`. The service depends on the authenticator package, Owner & Pet Manager, a mail channel, a reset-link template, and the Ed25519 private key. Replicas share this service’s database, so rotation locks and rate-limit caps hold across processes. Testing: use-case tests with fakes, Postgres tests for rotation, reuse, the sliding window, and the sweep, HTTP tests for wire collapses—not a multi-service end-to-end gate for this service alone.
